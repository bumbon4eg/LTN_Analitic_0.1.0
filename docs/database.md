# Подготовка PostgreSQL

Текущий Gateway подключается к PostgreSQL напрямую и при инициализации создаёт отсутствующие таблицы SQLAlchemy-моделей.

На текущем этапе проект использует как минимум:

```text
orders
order_events
```

---

## Рекомендуемая схема доступа

Используйте отдельную базу и отдельную учётную запись Gateway.

Пример для администратора PostgreSQL:

```sql
CREATE ROLE ltn_gateway LOGIN PASSWORD 'CHANGE_THIS_PASSWORD';
CREATE DATABASE ltn_analytics OWNER ltn_gateway;
```

После этого укажите в Gateway:

```text
Сервер:      адрес PostgreSQL
Порт:        5432
Имя базы:    ltn_analytics
Пользователь: ltn_gateway
Пароль:      <ваш пароль>
```

Конкретная политика прав зависит от способа размещения PostgreSQL. Главное требование текущей реализации — Gateway должен уметь подключиться к базе и создать отсутствующие таблицы при первом запуске.

---

## Принцип минимальных прав

Учётную запись Gateway не следует использовать как административную учётную запись PostgreSQL.

Рекомендуется:

- отдельный пользователь;
- отдельная база;
- отсутствие административных прав;
- только необходимые права на целевую схему;
- отдельный секрет для каждого окружения.

---

## SSL/TLS

Для удалённой БД рекомендуется использовать SSL/TLS.

В Gateway это включается флажком:

```text
Использовать SSL/TLS с проверкой сертификата сервера
```

Важно: текущая реализация использует стандартное доверенное хранилище сертификатов. Сервер должен предоставлять цепочку сертификатов, которой доверяет Windows/Python SSL context.

---

## Проверка вручную

До запуска Gateway можно проверить доступность БД отдельным клиентом PostgreSQL.

Например:

```powershell
psql -h <HOST> -p 5432 -U ltn_gateway -d ltn_analytics
```

После подключения:

```sql
SELECT version();
```

Если этот тест проходит, а Gateway нет, смотрите сообщение об ошибке Gateway и [docs/troubleshooting.md](troubleshooting.md).

## Что Gateway создаёт сейчас

Инициализация БД использует `Base.metadata.create_all`.

Это удобно для первого развёртывания, но не заменяет полноценную систему миграций. При развитии схемы проекта рекомендуется перейти на версионируемые миграции, чтобы изменения БД контролировались отдельно от запуска приложения.
